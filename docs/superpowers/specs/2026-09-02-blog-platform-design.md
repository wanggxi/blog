# Astro 博客与内容管理平台设计

日期：2026-09-02
状态：已完成会话设计确认，等待书面规格复核

## 1. 背景与边界（历史规格）

> 本文记录最初的 Astro 方案。经用户确认，公开前台已改为直接移植 `wan-kong/wankong.top` 的 Next.js 源代码；当前实施边界以 [`2026-09-02-wankong-frontend-transplant.md`](../plans/2026-09-02-wankong-frontend-transplant.md) 为准。

本项目在全新的 `wanggxi/blog` 仓库中建设个人博客、项目展示站和内容管理后台。公开站点使用 Astro，后台使用 Payload CMS。内容存储在 PostgreSQL 中，图片存储在 Cloudflare R2 中；发布文章不依赖 Git 提交或重新构建，正常情况下应在 5 秒内对外可见。

`wan-kong/wankong.top` 只作为内容型个人站的信息架构和视觉方向参考。项目不得复制其文章、项目、图片、头像、个人资料、品牌标识或未经许可的源码。初始站点使用明确的中性示例数据，真实资料由站长通过后台录入。

本规格包含应用架构、编辑与发布、数据安全、部署和验收要求。首次交付包含可运行代码、部署模板和文档；实际服务器部署在站长另行提供受限 SSH 凭据后执行。

## 2. 目标

- 提供原创、响应式、内容优先的个人博客和项目展示前台。
- 提供文章、项目、标签、图片、站点设置的统一管理后台。
- 同一篇文章同时支持富文本编辑和 MDX 源码编辑，且切换不丢失内容。
- 支持草稿、预览、即时发布、定时发布、撤回、历史版本和回滚。
- 当前可用 Docker Compose 部署到普通 Linux 服务器。
- Astro 前台未来可迁移到 Vercel 或 Cloudflare；Payload 后台可运行在普通服务器或 Vercel。
- 将部署结构、迁移、备份和 CI 配置纳入仓库，同时确保真实密钥永不进入 Git。

## 3. 非目标

首版不包含评论、会员注册、付费内容、邮件订阅、多人实时协作、复杂工作流审批、多语言内容、站内消息和通用页面搭建器。首版仅支持一个站长账号；数据模型可扩展角色，但不实现多角色界面和权限矩阵。

首版不承诺 Payload CMS 运行在 Cloudflare Workers。若未来要求整套系统迁移到 Cloudflare，需要单独评估和设计运行时兼容层或替换后台服务。

## 4. 总体架构

仓库采用 pnpm workspace 管理的单仓库结构：

```text
blog/
├── apps/
│   ├── web/                 Astro 公开站点
│   └── cms/                 Payload 管理后台与内容 API
├── packages/
│   ├── content-schema/      跨应用共享的数据契约和渲染树类型
│   └── mdx-pipeline/        MDX 解析、转换、校验和序列化
├── infra/
│   ├── docker/              容器配置
│   ├── caddy/               反向代理与 TLS 模板
│   ├── cloudflare/          Astro 的 Cloudflare 部署配置
│   └── vercel/              Astro/Payload 的 Vercel 部署说明
├── scripts/                 迁移、备份、恢复和健康检查
├── compose.yaml
├── .env.example
└── .github/workflows/       CI 与可选部署工作流
```

运行时关系：

```text
浏览器
  ├── 公开请求 ──> Astro ──> Payload Content API ──> PostgreSQL
  └── 管理请求 ──> Payload Admin/API ──────────────> PostgreSQL
                                               └──> R2

Payload 发布事件 ──签名请求──> Astro 缓存失效接口
```

Astro 和 Payload 只通过版本化 HTTPS API 及共享的数据契约耦合。Astro 不直接访问 PostgreSQL，避免迁移前台运行环境时携带数据库驱动和凭据。Payload 对外只暴露已发布内容；草稿只能通过已认证后台或有时效签名的预览请求获取。

## 5. 前台设计

### 5.1 页面范围

- `/`：个人介绍、最新文章、精选项目、社交链接。
- `/blog`：文章列表、标签筛选、关键词搜索和年份归档。
- `/blog/[slug]`：文章元数据、正文、目录、上一篇/下一篇、分享入口和返回顶部。
- `/projects`：项目列表、状态、标签、外部链接和关联文章。
- `/about`：个人介绍与联系方式。
- `/preview/[token]`：签名草稿预览；禁止索引并在过期后失效。
- RSS、Sitemap、`robots.txt`、规范链接、Open Graph 元数据和 404/500 页面。

站点外壳、错误页和不读取内容的 `/about` 可以预渲染。首页、博客列表、文章详情、项目列表、RSS 和 Sitemap 依赖当前发布数据，首版使用 Astro adapter 按需渲染，确保发布无需重新构建。后续只能在保持即时发布验收结果的前提下调整个别路由的渲染策略。

### 5.2 视觉原则

视觉采用原创的中性、现代、内容优先方向：清晰的排版层级、低干扰色彩、边框分隔、完善的亮暗主题、有限且尊重 `prefers-reduced-motion` 的动画。不得照搬参考站的组件尺寸、排版组合或品牌元素。

前台满足 WCAG 2.2 AA 的核心要求：键盘可操作、可见焦点、语义化标题、足够对比度、图片替代文本和跳转正文入口。

## 6. 后台设计

后台由 Payload Admin 提供基础框架，并扩展以下模块：

- 仪表盘：文章数量、草稿、定时发布、最近操作。
- 文章：筛选、搜索、双模式编辑、预览、发布、撤回和历史版本。
- 项目：增删改查、排序和关联文章。
- 媒体库：上传、检索、使用情况、复制地址和回收站。
- 标签：统一管理和使用计数。
- 网站设置：站名、简介、头像、社交链接和 SEO 默认值。
- 审计日志：登录、发布、撤回、删除和设置修改。
- 账号与安全：修改密码、TOTP 和恢复码。

后台应支持桌面与手机完成核心操作。复杂文章编辑以桌面为主要体验，但手机必须能够修改元数据、保存草稿、预览和发布。

## 7. 内容模型

### 7.1 Article

- `id`：稳定 UUID。
- `slug`：唯一、规范化、可显式修改。
- `title`、`summary`、`coverMediaId`。
- `sourceMdx`：不含 frontmatter 的正文唯一真实来源；标题、日期等元数据只存放在结构化字段中。
- `renderTree`：从 MDX 生成的安全、可移植渲染树；属于可再生派生数据。
- `plainText`：用于搜索和摘要生成的派生文本。
- `status`：`draft | scheduled | published | archived`。
- `publishedAt`、`scheduledAt`、`updatedAt`。
- `tags`、`seoTitle`、`seoDescription`、`canonicalUrl`。
- `version`：乐观并发控制版本号。
- `formatVersion`：MDX/渲染树格式版本。

Payload 的版本集合保存每次发布、撤回和手动快照。线上请求只读取当前已发布版本；编辑失败或新版本编译失败不得改变线上版本。

### 7.2 Project

- `id`、`slug`、`name`、`tagline`、`description`。
- `status`、`year`、`platform`、`tags`。
- `repositoryUrl`、`liveUrl`、`relatedArticleId`。
- `iconKey` 或 `iconMediaId`；`iconKey` 只能引用前台注册的图标白名单。
- `featured`、`sortOrder`、`published`。

项目数据不得包含 React 组件或任意代码。

### 7.3 Media

- 原始对象键、派生格式对象键、MIME、尺寸、字节数和文件哈希。
- `alt`、说明、上传时间、上传者和引用计数。
- 删除状态、回收站时间和最终删除时间。

### 7.4 其他集合

- `Tag`：名称、slug 和可选描述。
- `SiteSettings`：单例站点设置。
- `User`：首版只有一个 owner。
- `AuditEvent`：不可通过后台修改的追加式操作记录。

## 8. 双模式编辑器与 MDX 管道

`sourceMdx` 是唯一可人工修改的正文来源。富文本模式打开文章时将 MDX 解析为编辑器状态；保存时再确定性地序列化为 MDX。允许缓存编辑器状态以提高性能，但缓存可以随时重建，不能作为第二份权威正文。

富文本模式基于 Payload 的 Lexical 扩展；源码模式使用 CodeMirror。两者共享同一保存版本号。

支持的基础节点包括标题、段落、强调、链接、引用、列表、任务列表、表格、分隔线、图片和带语言的代码块。自定义组件通过注册表声明名称、属性 schema、可包含的子节点和对应前台渲染器，例如 `Notice`、`Callout`、`GithubCard` 和 `Steps`。

MDX 安全子集禁止：

- `import` 和 `export`。
- JavaScript 表达式和事件处理器。
- 未注册组件。
- 任意 HTML 脚本、iframe 和危险 URL 协议。

富文本无法解释的合法源码片段显示为原始 MDX 块并原样保留。未注册或不安全片段可以保存为草稿，但发布校验必须失败并给出行列、错误类型和修改建议。

发布时，MDX 管道完成文章元数据 schema 校验、语法解析、组件白名单校验、URL 清洗和渲染树生成。公开站点解释渲染树并映射到受控 Astro/React 组件，不在请求期间执行数据库中的 JavaScript 或动态编译任意 JSX。

## 9. 编辑、预览与发布流程

### 9.1 保存草稿

客户端携带 `version` 保存。服务器仅在版本匹配时更新并递增版本；不匹配时返回冲突信息和双方版本，不允许静默覆盖。编辑器定时保存服务器草稿，并在浏览器保存短期本地恢复副本。

### 9.2 预览

Payload 生成短时效、单用途或可撤销的签名 token。Astro 预览路由用 token 从 Payload 获取指定草稿版本，返回 `noindex, nofollow`，且不写入公共缓存。预览 token 不包含数据库凭据或正文。

### 9.3 发布

```text
锁定待发布版本
  -> 校验并生成 renderTree/plainText
  -> 在数据库事务中创建版本并切换 published 指针
  -> 写入审计事件
  -> 发送签名缓存失效请求
  -> 返回发布结果
```

数据库事务提交后内容即为已发布。缓存失效失败不会回滚已经正确发布的内容，而是进入重试队列；短 TTL 保证最终可见。正常情况下，从点击发布到公开访问看到新版本不超过 5 秒。

定时发布由 Payload 侧的可靠定时任务扫描到期记录，并复用同一发布事务。重复执行必须幂等。

## 10. 媒体管道

浏览器将文件发送到 Payload，由服务器校验实际文件类型、扩展名、大小和尺寸。SVG 默认拒绝；未来若开放必须使用严格清洗和独立响应头。

媒体存储通过 S3 兼容接口抽象。生产环境使用 R2；本地开发和自动化测试使用 MinIO 或内存测试适配器，不要求开发者持有生产凭据。

通过校验的图片上传到对象存储，保留原图并由服务端生成 WebP、AVIF 和缩略图。对象键包含内容哈希，避免重名和重复上传。数据库记录只在必要对象上传成功后写入；数据库写入失败应清理本次产生的孤立对象。

删除媒体先进入 30 天回收站。仍被已发布内容引用的媒体不得永久删除。公开图片使用独立媒体域名和长期缓存；对象使用不可变键，更新图片生成新键。

## 11. 认证与安全

- Payload 注册入口关闭，通过一次性运维命令创建首个 owner。
- 登录使用邮箱、强密码和 TOTP；初始化时生成一次性恢复码。
- 会话 Cookie 使用 `HttpOnly`、`Secure` 和合适的 `SameSite` 策略。
- 所有状态修改请求执行 CSRF/Origin 校验；登录和敏感接口限流。
- 管理 API 默认拒绝匿名访问；内容 API 仅返回已发布字段。
- 预览、缓存失效和内部任务使用不同用途的签名密钥。
- 审计登录成功/失败、发布、撤回、删除、恢复和设置变更。
- 日志不得记录密码、完整 token、Cookie、数据库 URL 或 R2 密钥。
- 依赖扫描和安全更新进入 CI；高危漏洞阻止发布。

## 12. 缓存与可移植性

首版不引入 Redis。Astro 内容客户端和缓存失效逻辑通过小型接口隔离平台差异：

- 普通服务器：请求 Payload API，使用进程内短缓存和 HTTP 缓存头；单实例重启不影响正确性。
- Vercel：使用平台支持的缓存/失效能力。
- Cloudflare：使用 Cache API 或等价 adapter 能力。

文章、首页、博客列表、项目列表、RSS 和 Sitemap 都有明确的失效键。发布文章时失效文章详情及所有包含它的聚合页面。主动失效失败至少重试三次，并由短 TTL 保证最终一致性。

缓存层只能影响性能和短暂新鲜度，不能成为内容真实来源。预览、后台和认证响应禁止公共缓存。

## 13. 部署设计

### 13.1 当前服务器

Docker Compose 运行：

- `web`：Astro Node adapter。
- `cms`：Payload。
- `worker`：运行 Payload 后台任务，负责定时发布、缓存失效重试和媒体最终清理。
- `postgres`：PostgreSQL。
- `caddy`：TLS、反向代理和安全响应头。
- `backup`：受限的定时备份任务。

本地开发 profile 可以额外启动 MinIO；生产 profile 直接连接 R2，不启动本地对象存储。

域名通过环境变量配置，推荐拆分为公开站、后台和 API 三个主机名。`.env.example` 只列变量名、用途和生成方法，不含真实值。数据库与后台端口不直接暴露公网。

### 13.2 Vercel 与 Cloudflare

Astro 可改用 Vercel 或 Cloudflare adapter，继续通过同一 Content API 获取数据。Payload 可迁移到 Vercel，或继续运行在当前服务器。PostgreSQL 和 R2 保持独立，因此迁移前台不迁移数据。

Cloudflare 部署不包含“Payload 直接运行在 Workers”的承诺。若 Payload 留在服务器，必须配置受限 CORS、TLS 和 API 限流。

### 13.3 CI/CD

每个 Pull Request 执行格式检查、类型检查、单元测试、集成测试、端到端核心冒烟测试和生产构建。数据库迁移必须向前兼容当前部署版本，并在应用更新前备份。

可选部署工作流通过 GitHub Actions Secrets 获取服务器地址和部署私钥。SSH 私钥、服务器密码、数据库 URL、Auth 密钥、R2 密钥和 GitHub token 不得进入仓库或构建产物。

## 14. 备份与恢复

PostgreSQL 备份加密后写入独立的 R2 备份 bucket：每日备份保留 7 份，每周保留 4 份，每月保留 6 份。备份包含 schema、数据和恢复所需的版本元数据。

媒体使用不可变对象键和 30 天回收站。数据库备份保存媒体引用、哈希和对象键；备份脚本同时生成媒体清单以检查缺失对象。

每季度在隔离环境执行恢复演练：恢复数据库、验证 owner 登录重置流程、抽查文章版本、项目、媒体引用和公开 API。恢复文档必须包含从空服务器开始的步骤。

## 15. 错误处理与可观测性

- MDX 错误返回稳定错误码、行列和可操作信息，不泄露服务器堆栈。
- 发布失败保留线上旧版本，并允许继续编辑失败草稿。
- R2 或数据库暂时故障使用有上限的指数退避；非幂等操作使用请求 id 防止重复。
- 定时发布、缓存失效和媒体清理任务记录状态、尝试次数和最终结果。
- 提供不泄露敏感信息的 Web/CMS 健康检查。
- 使用结构化日志关联请求、用户、文章版本和后台任务。
- 生产环境捕获未处理异常并发送告警；告警服务通过可替换接口接入。

## 16. 测试策略

- 单元测试：schema、slug、URL 清洗、权限、MDX 解析/序列化、白名单和渲染树。
- 属性/夹具测试：富文本到 MDX 再返回编辑器状态的稳定往返，覆盖所有注册组件。
- 集成测试：数据库迁移、草稿、发布、撤回、定时发布、回滚、并发冲突和审计记录。
- 媒体测试：格式伪装、超限文件、重复文件、派生格式、孤立对象清理和引用保护。
- Playwright：owner 登录、TOTP、双模式编辑、上传、预览、发布和回滚主路径。
- 安全测试：匿名访问、越权、CSRF、XSS、恶意 MDX、危险 SVG 和 token 过期。
- 部署测试：容器启动、迁移、健康检查、反向代理和从备份恢复。

## 17. 验收标准

- 富文本与 MDX 模式往返不会丢失受支持的内容或白名单组件。
- 不支持的源码可保存在草稿中并明确标记，但不能绕过发布校验。
- 正常情况下发布后 5 秒内公开站可见；无需 Git 提交或全站重新构建。
- 新版本发布失败时，线上旧版本持续可用。
- 历史版本可查看并一键回滚；误删内容和媒体可在回收期内恢复。
- 文章、项目、媒体、标签和站点设置都能从后台管理。
- 手机和桌面均可完成核心后台流程。
- 前台包含正确的 SEO、RSS、Sitemap、404/500 和无障碍基础能力。
- `compose.yaml`、部署文档和 `.env.example` 足以在新服务器重复部署。
- CI、仓库历史和构建产物不包含真实密钥。
- 参考站的个人内容、资产和品牌信息不出现在交付物中。

## 18. 实施顺序

实施计划将把本规格拆为可独立验证的阶段：工作区与基础设施、共享内容契约、Payload 数据层与认证、MDX 管道、双模式编辑器、Astro 前台、发布与缓存、媒体与备份、端到端验证及部署文档。每个阶段都必须保留可运行状态，并在进入下一阶段前通过对应质量门。
